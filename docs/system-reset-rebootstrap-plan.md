# خطة إعادة تأسيس النظام من الصفر (Production)

## الهدف
تنفيذ إعادة ضبط كاملة لبيئة archive-tech (حذف المستخدمين والإدارات وكل البيانات التشغيلية المرتبطة)، ثم إعادة إنشاء مدير النظام الأساسي من البداية، وبعدها إعادة إنشاء الإدارات والمستخدمين بحيث تكون الإدارة مركزية بالكامل من خلال مدير النظام.

## القرارات المعتمدة
1. البيئة: Production (archive-tech).
2. نطاق الحذف: حذف شامل لكل البيانات المرتبطة.
3. سجلات التدقيق: حذفها أيضا، ولكن بعد التصدير الاحتياطي.
4. حساب مدير النظام الأول: kareemqotp@gmail.com.
5. أسلوب Bootstrap: Admin SDK مباشر (لتفادي أي قيود allowlist في الواجهة).

## مبادئ الأمان قبل التنفيذ
1. لا يتم تنفيذ أي حذف قبل نجاح النسخ الاحتياطي الكامل.
2. لا يتم حذف كل المستخدمين قبل تجهيز مسار bootstrap المؤكد.
3. يتم التنفيذ على مراحل مع نقطة تحقق بعد كل مرحلة.
4. أي فشل في مرحلة حرجة يوقف التنفيذ فورا ويتم الرجوع لخطة rollback.

## المرحلة 0: Preflight
1. تفعيل نافذة صيانة وإيقاف العمليات الكتابية من الواجهة.
2. التقاط baseline سريع:
   - عدد users.
   - عدد departments.
   - عدد collections التشغيلية الأساسية.
3. التحقق من صلاحية Service Account المستخدمة في Admin SDK.
4. التحقق من وجود صلاحية تشغيل أوامر Firebase/Node على بيئة التنفيذ.

## المرحلة 1: النسخ الاحتياطي الإلزامي
1. تصدير Firestore كاملا إلى موقع backup موثق.
2. تصدير Firebase Auth users إلى ملف منفصل.
3. تصدير منفصل لسجلات audit_logs وactivity_logs وauth_logs للاحتفاظ المرجعي.
4. توثيق مسارات ملفات النسخ الاحتياطي في سجل تنفيذ واحد.

## المرحلة 2: الحذف الشامل المنظم

### 2.1 حذف المجموعات التابعة أولا (Dependency-first)
يتم حذف المجموعات التالية بالترتيب:
1. notifications
2. shared_links
3. file_movements
4. transfers
5. transfer_requests
6. client_files
7. clients
8. documents
9. user_preferences
10. user_page_permissions
11. invitations

### 2.2 حذف سجلات التدقيق بعد التصدير
1. audit_logs
2. activity_logs
3. auth_logs

### 2.3 حذف المستخدمين والحاويات الأساسية
1. حذف جميع مستخدمي Firebase Auth.
2. حذف users.
3. حذف departments.
4. حذف system_settings.

### 2.4 سياسة التحقق أثناء الحذف
بعد كل Collection:
1. تسجيل count قبل الحذف.
2. تنفيذ الحذف.
3. تسجيل count بعد الحذف.
4. تسجيل النتيجة (نجاح/فشل + رسالة الخطأ عند الفشل).

## المرحلة 3: إعادة تأسيس مدير النظام (Bootstrap)
1. إنشاء حساب kareemqotp@gmail.com في Firebase Auth.
2. تعيين Custom Claims:
   - role = super_admin
   - department حسب السياسة المعتمدة.
3. إنشاء/تحديث مستند users/{uid} بالقيم الدنيا:
   - uid
   - email
   - role = super_admin
   - isActive = true
   - createdAt/updatedAt
   - roleAssignedAt/roleAssignedBy
4. التحقق الفني:
   - claimsRole = super_admin
   - docRole = super_admin

## المرحلة 4: إعادة بناء الهيكل التشغيلي
1. إعادة إنشاء الإدارات الأساسية.
2. إنشاء Admin لكل إدارة (بصلاحيات محددة للإدارة فقط).
3. إنشاء مستخدمي الإدارات من خلال مدير النظام.
4. إعادة تهيئة system_settings الأساسية:
   - إعدادات الجلسات
   - lockout
   - feature flags
   - أي إعدادات حرجة مطلوبة لتشغيل البوابة.

## المرحلة 5: التحقق النهائي قبل فتح النظام
1. التحقق من الوصول:
   - super_admin يصل لكل الصفحات الحساسة.
   - admin الإدارة يصل فقط لنطاقه.
2. التحقق الوظيفي:
   - إدارة الإدارات تعمل.
   - إدارة المستخدمين تعمل.
   - إنشاء Admin إدارة يعمل.
3. التحقق الأمني:
   - العمليات الحساسة تتطلب السبب reason حيث يلزم.
   - لا توجد privilege escalation غير مصرح بها.
4. إنهاء نافذة الصيانة بعد نجاح اختبارات smoke.

## خطة Rollback (مختصرة)
في حال فشل أي مرحلة حرجة:
1. إيقاف التنفيذ مباشرة.
2. عدم متابعة الحذف أو إعادة البناء.
3. استرجاع Firestore من النسخة الاحتياطية الأخيرة.
4. استرجاع Auth users من نسخة التصدير.
5. إعادة التحقق من الوصول لحسابات الإدارة الأساسية.
6. فتح incident report بسبب الفشل وتحديد سبب جذري قبل أي محاولة جديدة.

## نقاط فشل حرجة يجب مراقبتها
1. فشل التصدير الاحتياطي.
2. فشل حذف جزئي يسبب بيانات معلقة.
3. حذف كامل للمستخدمين بدون نجاح bootstrap.
4. تعارض claims مع role داخل users.
5. Feature flags أو system_settings تمنع دخول super_admin بعد إعادة البناء.

## مخرجات التنفيذ المطلوبة
1. سجل تنفيذي زمني لكل خطوة.
2. تقرير counts قبل/بعد لكل مجموعة.
3. توثيق نتيجة bootstrap مع uid النهائي لمدير النظام.
4. تقرير تحقق نهائي (Access + Functional + Security).

## ملاحظات تنفيذية
1. التنفيذ المباشر على Production عالي المخاطر، ويفضل تجربة نفس السكربتات على Emulator أولا.
2. أي خطوة حذف يجب أن تكون idempotent قدر الإمكان.
3. لا يتم الانتقال للمرحلة التالية إلا بعد نجاح تحقق المرحلة الحالية.
